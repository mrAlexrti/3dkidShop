# Batch 1.5 — notification and status architecture audit

Audited 2026-11-12. Findings describe the current code, not observed production delivery. Credentials, provider configuration values, production cron scheduling, and real recipient delivery were not inspected or exercised. **No notification/status redesign was implemented.** No real payment, email, Telegram message, or TTN was created.

## Source map and shared delivery behavior

- `src/lib/actions/create-order.ts` — `createOrder`, `priceOrderItems`: server-authoritative product/size prices, transactional stock reservation/order creation, online handoff, offline notification trigger.
- `src/lib/notifications/orders.ts` — `notifyOrderCreated` concurrently calls `sendCustomerOrderEmail` and `notifyNewOrder` through `Promise.allSettled`. Only the email sent boolean is returned. `notifyOrderStatusChanged` sends Telegram only and exits when old/new OrderStatus match.
- `src/lib/notifications/email.ts` — `getEmailConfig`, `sendEmail`: Resend HTTP transport gated by `RESEND_API_KEY` and `EMAIL_FROM`, addressed to the order's customer email. `ADMIN_EMAIL` is read but unused. No owner-email copy, provider idempotency key, queue, delivery log, or retry loop.
- `src/lib/notifications/telegram.ts` — `getTelegramConfig`, `sendTelegramMessage`: one env-configured owner/admin chat, gated by `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ADMIN_CHAT_ID`. Errors return false; callers generally discard this outcome. No customer Telegram subscription or per-order recipient.
- `src/lib/email.ts` — `sendOrderConfirmationEmail`: compatibility re-export of `sendCustomerOrderEmail`; no second transport or independent trigger. No runtime call site found for this alias.
- `src/lib/payments/online-payment.ts` — `getOnlinePaymentConfig`: only explicitly configured LiqPay sandbox mode with sandbox-looking keys is available. Live acquiring is disabled by code. Key presence alone cannot enable it.

**Localization used by the event matrix:** `UA-template` means hardcoded Ukrainian text in `src/lib/notifications/orders.ts` (`renderCustomerOrderEmail`, `renderTelegramNewOrder`, `renderTelegramStatusChanged`, `deliveryLabel`, `paymentNote`, `formatDate`), not the centralized UA/EN dictionary. Status labels come from Ukrainian-only `src/lib/order-status.ts` — `getOrderStatusLabel`; size labels use `orderSizeLabel` with default UA. `createOrder` snapshots product names from the UA database field. No Order locale is persisted. Choosing EN at checkout changes validation/UI but does not produce an English notification.

**Active** below means there is a reachable code path if its env/service prerequisites are satisfied. It does not assert any secret is present or cron is scheduled. **Admin configurable: No** applies to every matrix row: there are no event/channel notification toggles in the current Admin. Missing events have no recipient or localization implementation.

## Risks requiring separate approval

1. **Critical payment/delivery classification risk — confirmed isolated reproduction.** `src/app/api/cron/novaposhta/route.ts` — `isCodPaidStatus` accepts substring `paid`, including `unpaid` and `not paid`, and Ukrainian negative phrases containing its accepted stems. `isDeliveredStatus` likewise accepts `not delivered`. Actual private predicate source was evaluated in an isolated VM: all three negative English samples returned true, with no DB/network calls. This proves classifier behavior, not that NP has returned those exact strings or any production order has been misclassified. In `GET`, a false paid classification sets paidAt and can lead to COMPLETED; raw COD detection is not restricted to COD-method orders. Recommend verified provider-code allowlists and unknown/manual-reconciliation handling before relying on automated payment facts. No fix made.
2. **TTN creation is not proof of shipment.** `src/lib/order-status.ts` — `getOrderStatusAfterTtnCreated` unconditionally returns SHIPPED for nonfinal orders. `src/app/api/admin/orders/[id]/create-ttn/route.ts` — `POST` has no concurrent reservation around the external create. `src/components/admin/create-ttn-button.tsx` disables its own button while loading but is not a server concurrency lock or confirmation. No fix made.
3. **State/delivery loss windows.** Callback `POST` commits its CAS before notification sending; retries see the committed state and skip sending. Offline `createOrder`, Admin `updateOrderStatus`, and cron `GET` also have no durable delivery retry or outbox. Cron/manual read-then-write can regress state under concurrency. No fix made.
4. **Stock reservation lifecycle is incomplete.** `src/lib/actions/create-order.ts` — `createOrder` decrements stock before online completion. Failure/cancellation/refund handlers and manual cancellation have no reservation release; this is existing behavior, not introduced by Phase 1. A release policy needs idempotency and cancellation/payment reconciliation rather than an unconditional increment. No fix made.
5. **Sandbox isolation is local to the payment callback.** Callback `POST` suppresses its sandbox notifications, but `notifyOrderStatusChanged`, manual Admin updates, TTN creation, and cron have no universal sandbox/test-mode channel suppression. A manually edited sandbox order can reach owner Telegram if configured. No real such actions were executed.
6. **Transport observability and logs.** `sendEmail`/`sendTelegramMessage` return unsuccessful results without a durable record; response bodies and caught error messages are logged. Future work should sanitize provider errors and record delivery outcomes without credentials, capability tokens, or unnecessary customer data. No logs containing credentials were intentionally emitted in this batch.

## Minimal event/channel configuration proposal — not implemented

`src/app/admin/content/page.tsx` currently edits hero/social/font content; its Telegram field is a public social URL. `src/lib/site-content.ts` only allowlists storefront content keys. `src/components/admin/admin-sidebar.tsx` has no notification settings destination. Neither that UI nor existing transports provide event toggles.

Smallest initial policy could be a server-only typed JSON key such as `notification_policy_v1` in existing `SiteContent`, accessed through separate ADMIN-only actions and Zod validation. Do not add it to the public storefront-content allowlist, put credentials in it, or expose secrets in Admin.

One row per stable event, with two independent booleans:

| Event policy field | Meaning |
| --- | --- |
| `ownerTelegram` | Send this event to the configured owner/admin chat. |
| `customerEmail` | Send this event to the order's customer email. |

Use events for order.created, payment.pending/paid/failed/cancelled/refunded, delivery.ttn_created/shipped/in_transit/arrived/delivered/returned, order.status_changed/cancelled/completed. Manual changes to CANCELLED/COMPLETED should produce the specific event instead of also sending the generic one. Multiple facts changing in one sync need an explicit coalescing rule; changing OrderStatus must not accidentally suppress a delivery event.

Absent policy should preserve today's reachable behavior: offline new-order email+Telegram and generic owner status Telegram enabled; all newly introduced customer messages/events disabled until templates/triggers are approved. Hide or disable toggles for events without implemented support. Keep sandbox/provider safety gates stronger than toggles, with no real-recipient preview action. Owner locale can default UA; customer locale must come from a future persisted order snapshot. Show delivery failure state without exposing keys.

This policy can reuse the current schema initially. **Reliable notification delivery cannot be solved by toggles alone:** a durable event/outbox and unique delivery identity are separate schema work. Prefer `(eventId, channel, recipient identity)` uniqueness with a transactional state transition/outbox write, queued retry, and provider idempotency where supported. Do not promise exactly-once Telegram delivery across ambiguous network failures.

## Recommended normalized model — proposal only

Keep Prisma, provider adapters, checkout pricing, and authorization. Add facts alongside legacy fields first; backfill with a review report, reconcile ambiguity, then switch consumers. No bulk conversion in this batch.

| Domain | Proposed base states | Transition rule |
| --- | --- | --- |
| Order lifecycle | NEW, CONFIRMED, PROCESSING, COMPLETED, CANCELLED | Business handling only. COMPLETED normally requires delivery completion and the approved payment condition; authorized manual exceptions need recorded reason. Cancelling an order must not erase payment or delivery facts. |
| Payment | PENDING, PAID, FAILED, CANCELLED, REFUNDED; an explicit UNKNOWN/REVIEW path for legacy ambiguity | Confirm paid only from authoritative payment evidence, or an audited manual bank-transfer confirmation. Keep attempt/provider/mode/transaction reference and raw provider status separate. COD collection and merchant settlement are different facts. Refund amount and partial refunds must not be inferred from a single boolean. Browser exit alone does not mean CANCELLED. |
| Delivery | NOT_CREATED, TTN_CREATED, SHIPPED, IN_TRANSIT, ARRIVED_AT_BRANCH, DELIVERED, RETURNED; allow UNKNOWN/EXCEPTION and, when supported, RETURNING | A TTN is a document; SHIPPED requires carrier acceptance. Arrival includes locker pickup availability. Return initiation differs from completed return. Unknown codes retain raw evidence and must not be guessed from translated substrings. |

Migration candidates, **not automatic mappings**: legacy PENDING -> lifecycle NEW; AWAITING_PAYMENT -> NEW plus payment PENDING; PROCESSING -> PROCESSING. PAID supplies a candidate payment fact but needs paidAt/provider/manual evidence before migration. SHIPPED must be reconciled against tracking because existing TTN creation assigned it early. DELIVERED supplies a candidate delivery fact; COMPLETED/CANCELLED require review for inconsistent payment/delivery evidence. Preserve raw fields and historical size/name/price snapshots.

Provider adapter work must confirm exact API version, signatures, status code meanings, and authoritative settlement evidence before implementation. The [official LiqPay payment-status reference](https://www.prod.liqpay.ua/uk/doc/api/information/status_payment?tab=1) distinguishes terminal success/failure/refund from processing, verification, held, and waiting states. Therefore a future adapter needs explicit pending/unknown handling rather than treating every non-success as failure. This is a recommendation inferred from that reference; it does not change the existing v3 sandbox adapter. No authoritative full NP code mapping was verified in this audit; implementing it requires the applicable official NP contract and sanitized fixtures, not guessed numeric codes.

Public labels/templates must use central UA/EN dictionaries with a neutral localized unknown/review fallback, never raw technical codes. Persist order locale (UA default, EN supported); localize notification templates and future customer tracking separately from Admin diagnostic raw fields. No Russian locale, customer account, new payment provider, COD redesign, or live activation is part of this proposal's implementation in this batch.
