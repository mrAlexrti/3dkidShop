# Batch 1.9 customer account

Local release review **READY**. Production readiness is pending separate operator approval, database preflight and migration, Google OAuth and Resend configuration, and real-provider smoke tests.

## Implementation

- The storefront uses the existing 3D Kid components and UA/EN dictionaries. The header account link opens sign-in or the private account. Account navigation covers profile, favorites, order history, order detail and sign-out.
- Auth.js 5 Google OIDC and credentials share the existing `User`, `Account` and `Session` models. Customer auth has its own route, secret and cookie namespace. Auth.js encrypts the HttpOnly Lax session cookie. The database stores a hash of its opaque session handle. HTTPS uses host-only secure cookies. Sessions have a 14-day absolute expiry. The existing environment-configured admin login keeps its own cookies and role checks.
- The lockfile pins Next.js 15.5.29, Auth.js 5.0.0-beta.32 and Sharp 0.35.5 for the published auth, routing and image optimizer fixes. React and React DOM 19.2.9 replace the previous release candidate and satisfy the patched packages' peer requirements. [Next.js security release](https://github.com/vercel/next.js/releases/tag/v15.5.29) · [Auth.js provider binding advisory](https://github.com/nextauthjs/next-auth/security/advisories/GHSA-x445-f3h2-j279) · [Sharp minimum version](https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw)
- Native registration verifies email before accepting a password. bcryptjs uses cost 12. Registration, recovery, account email verification, adding a password, email changes and claims use expiring single-use random proofs whose hashes are stored in PostgreSQL. Password reset, adding a password and email changes revoke customer sessions. Verified email changes require confirmation from the current and new addresses in the signed-in browser. Login, registration and recovery use generic responses. Resend sends eligible public email requests after the response to keep provider latency out of it.
- Google provides the verified OIDC subject. Auth.js checks PKCE, state and nonce. The account lookup uses the provider and subject. New Google-only accounts require Gmail or a Google Workspace address. Customers who use Google with an externally hosted email first verify their mailbox through native registration. Existing customers connect Google from their profile by confirming their password and completing OAuth with the same address. Google-only users can add native sign-in from a signed-in session with fresh mailbox proof. The database stores the Google subject and internal user association without Google access or refresh tokens. [Google OIDC claims](https://developers.google.com/identity/openid-connect/reference) · [Google email authority](https://developers.google.com/identity/sign-in/ios/backend-auth)
- Customer writes resolve identity from the server-side session and check the request origin. Private pages query by owner as part of the same order or favorite lookup. Account, checkout prefill and favorites responses are private and uncached. PostgreSQL rate buckets coordinate across app instances. Profile phone is contact information. Admin pages, mutations and protected APIs retain server-side admin checks.
- Up to 200 guest favorites are stored on the device and merged idempotently on sign-in. The customer/product primary key prevents duplicates. The favorites view uses current catalog prices and manufacturing availability. Inactive products disappear from the list and return if restored to the catalog. Deleted products cascade out of favorites.
- Checkout accepts absent or cleared email and stores it as SQL `NULL`. A verified account email is a prefill only. Recipient name, surname, phone, delivery and payment inputs stay required as applicable. Order ownership is assigned in the authoritative server transaction. Gift recipients and different contact details stay separate. Owner checks also apply to checkout replay. The Mono invoice omits `customerEmails` for an empty contact. NovaPay COD uses Nova Poshta's shipment and money-return fields through the existing adapter. Those requests use recorded recipient and phone data. The existing notification paths skip customer email delivery for absent recipients and preserve Telegram behavior. [Mono acquiring API](https://api.monobank.ua/docs/acquiring.html) · [NovaPay COD](https://novapay.ua/pisljaplata/)
- Order history uses accepted and operational historical orders. It displays recorded recipient details, unit prices, quantities, variants, totals, payment and delivery status and tracking where present. The detail page preserves the recorded address when an older order has no branch snapshot and localizes historical COD aliases. New orders save an image URL selected from the authoritative gallery. Older orders use an available general image or placeholder. There is no persisted discount field in the existing order model.
- Guest link requests require a signed-in customer with a verified address, the public order number and an eligible unowned order with the same recorded contact address. The customer must then redeem the emailed order-specific token in the requesting session. The transaction applies ownership only while the order is still unowned. Historical records with eligible email can use the same flow. Guest orders with absent or unusable email stay independent. Future verified phone and SMS claims can add a new challenge purpose and retain the same guarded ownership write. A future claim proof issued at checkout would use a dedicated, single-use token separate from the order-status link.
- UX-02 displays requirement and alternative counts, material availability, blocking group positions, and the separate manual disable state. Each row links to the variant editor. Admins can inspect this summary on inactive products.
- UX-03 exposed an unordered query and no stored option-value position. The migration leaves positions unset. The default recognizes standard sizes from either saved label, independent of the active storefront locale, and uses a deterministic ID tie-breaker for other labels. Open **Admin → Products → Edit → Product variants** and use **Move up** or **Move down**, then save, to persist an explicit order for a dimension. Locale, color selections, merchant switches and filament availability leave the button order intact. Values, variants, gallery bindings, requirements, and historical snapshots keep their IDs.
- UX-04 aligns prices and cart buttons within each catalog row. The grid already stretched the cards to equal heights, while the card body sized to its contents. The body now fills the card and pushes the price and cart row to the bottom. Product titles still wrap in full, including long titles with localized “from” prices.

## Release review findings

- OAuth initiation and callback use the configured canonical origin for the Auth.js request and Google token exchange. The start endpoint checks literal `Host` and browser `Origin` before invoking the framework, accepts only bounded URL-encoded POSTs, and validates the outbound Google destination. The callback checks the literal `Host` and uses Auth.js state, nonce and PKCE cookies. On Vercel, the provider IP header is used only to key the throttle. Return destinations are fixed. An explicit Google link is bound to the active account, session and OAuth state. Its intent survives sign-out until the short cookie expires, while the revoked session cannot finish the link. [Vercel request headers](https://vercel.com/docs/headers/request-headers)
- Session reads accept the named HttpOnly cookie, verify the Auth.js ciphertext and resolve a live customer session in PostgreSQL. Profile, favorite and claim writes recheck the server session under a customer row lock. Favorites bind the browser view to its session so a stale tab cannot write to another account after sign-in changes. The admin middleware uses only the admin cookie, admin pages assert their role before database work, and TTN creation checks both the admin role and request origin. Account and checkout prefill responses are private and uncached.
- Verification, recovery and claim tokens are cryptographically random, stored as SHA-256 digests and consumed with one conditional `DELETE … RETURNING`. The database UTC clock controls expiry, including on servers configured in another timezone. Session-bound tokens require the intended customer and session before consumption. Concurrent submissions cannot redeem the same proof twice, and competing claims cannot reassign an order. A timeout or ambiguous response from Resend leaves the proof usable until expiry. Confirmed failures remove it. Public registration and recovery keep a generic response. The sign-in password bound is 72 UTF-8 bytes for bcrypt, and native registration requires at least 12 characters.
- Existing payment capabilities still work for guest orders. An authenticated payment retry checks the original order's owner before querying the provider and again after refreshing payment evidence. Claiming an order or updating a profile leaves recorded order contact, line snapshots, totals and payment history intact. Database triggers also protect assigned owners and historical image snapshots. Old items with no saved image use an available product image or the placeholder.
- NextAuth and the direct dependency resolve to the same `@auth/core@0.41.3`. Registry TLS remained enabled. The security review updated Zod and its form resolver together, updated Next's PostCSS dependency and patched the audited lint and build transitive dependencies. The optimized build reaches JOSE's optional JWE `zip=DEF` branches through the admin Edge middleware. These branches reference `CompressionStream` and `DecompressionStream`, which the Next.js compiler flags for Edge. Auth.js emits encrypted session headers containing `alg`, `enc` and `kid`, so sessions do not enter those branches. The local optimized middleware and admin login were exercised with the ordinary Auth.js cookie format. Keep the Vercel smoke test as a release gate.

## Neon workload and caching

- The disposable PostgreSQL sample included 100 products, 600 variants, 1,200 requirement groups, 20 accounts, 160 favorites and 49 orders at seven per day. Catalog price sorting and relation loading used 12 Prisma statements per 24-product page regardless of the page position. Switching a filament moved the next authoritative minimum price from 102 to 12. The sample measures local statements and correctness. Use Neon telemetry after approval to measure Production compute and latency.
- Storefront font and footer content share one request-scoped settings read. Public browsing does not require a server-side customer lookup. Guests without a customer cookie make no session query. Favorites fetch on startup, account boundaries and bounded focus refresh, then use mutation results and cross-tab events for synchronization. Authenticated tabs broadcast a refresh marker without storing private favorites in the browser. Account pages memoize their session read within the render. Authentication rate buckets update in one PostgreSQL statement.
- Reuse the Prisma client per warm runtime and use the existing restricted Neon pooled connection for `DATABASE_URL`. Use a separate direct owner connection for psql release scripts. The customer feature adds no periodic polls or scheduled tasks. Keep existing payment and delivery task schedules under operator review, since frequent calls can wake an otherwise idle compute. [Neon pooling](https://neon.com/docs/connect/connection-pooling) · [Neon with Prisma](https://neon.com/docs/guides/prisma)
- Catalog and product-detail reads use the existing public query path and live availability. Cart reconciliation coalesces in-flight matches, skips empty carts and stays separate from the authoritative checkout transaction. Consider profiling public metadata and catalog joins after launch, and paginate favorites if real collections grow substantially. Any future public cache needs price and filament invalidation. Personalized reads stay private.

## External configuration

Use a separate local database and development OAuth client. The pinned Sharp package requires Node.js 20.9.0 or newer. Configure Production after rollout approval.

| Setting | Local example | Production |
| --- | --- | --- |
| `CUSTOMER_AUTH_ORIGIN` | `http://localhost:3000` | `https://www.3dkid.shop` |
| `CUSTOMER_AUTH_SECRET` | Random independent secret of at least 32 characters | A different random server secret |
| `CUSTOMER_GOOGLE_CLIENT_ID`, `CUSTOMER_GOOGLE_CLIENT_SECRET` | Local OAuth client | Production OAuth client |
| `RESEND_API_KEY`, `EMAIL_FROM` | Verified sender and sending key for approved mailbox tests, or mock locally | Existing or approved domain-scoped sending key and verified sender |

Keep `AUTH_SECRET` or `NEXTAUTH_SECRET`, `AUTH_URL` or `NEXTAUTH_URL`, `ADMIN_USERNAME` and `ADMIN_PASSWORD_HASH` for the existing administrator login. Keep `AUTH_DEBUG=0` in Production. `ADMIN_EMAIL` is existing notification configuration and is optional for customer authentication. If the customer origin or secret is missing, customer authentication fails closed. If the Google variables are missing, Google sign-in is unavailable. If the Resend variables are missing, email-dependent registration, reset, email change and claim are unavailable.

### Google OAuth

1. In Google Cloud, create or select the project and open **Google Auth Platform → Branding**. Set the 3D Kid name, support email, developer contact, authorized domain `3dkid.shop`, canonical HTTPS homepage and the public privacy policy. Verify domain ownership and complete any brand verification requested in the console. [Google production and verification requirements](https://developers.google.com/identity/verification/authentication-policy-compliance)
2. Under **Audience**, choose **External**. Add operator-controlled Gmail or Workspace users during Testing and switch to **In production** after completing applicable console requirements. Under **Data Access**, request only `openid`, `email` and `profile`. These basic identity scopes are sufficient for sign-in and linking. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
3. Under **Clients**, create separate **Web application** clients for local and Production. Register `https://www.3dkid.shop/api/customer-auth/callback/google` on the Production client. Register `http://localhost:3000/api/customer-auth/callback/google` for local use, or `http://127.0.0.1:3000/api/customer-auth/callback/google` if `CUSTOMER_AUTH_ORIGIN` uses that host. Authorized JavaScript origins are optional for this server flow. If filled, enter the matching origin with no path. [Google server-side OAuth setup](https://developers.google.com/identity/protocols/oauth2/web-server)
4. Store the client ID and secret in the corresponding server environment. Set the exact customer origin and an independent customer auth secret. After separate approval, test consent, account selection, callback origin, cookie persistence, native-to-Google linking and rejection of unlinked matching email on real operator-controlled accounts and devices.
